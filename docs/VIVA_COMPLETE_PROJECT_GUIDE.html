2.0 Problem Statement & Real-World Motivation

The Ground Reality in Local Outpatient Clinics

In India and across developing healthcare systems, local private and public community health clinics operate with high patient-to-doctor ratios. Unlike major tertiary hospitals, local community clinics do not possess enterprise hospital management software (HIS) or digital turnstiles.

1. Physical Crowding & Infection Hazards
Patients arrive all at once at clinic opening time. Waiting rooms become congested, causing airborne cross-infection hazards between immunocompromised seniors, pediatric patients, and contagious walk-ins.
2. Opaque, Unpredictable Waiting Times
Patients have no visibility into how fast the doctor is consulting. A patient told "you are 5th" may wait 25 minutes or 90 minutes with zero updates, causing anxiety, front-desk disputes, and walk-away no-shows.
3. Manual Paper Register Overhead
Receptionists record tokens in physical registers. Paper records are prone to illegible handwriting, duplicate numbers, queue jumping disputes, and lost patient contact histories.
4. Doctor Schedule Desynchronization
Doctors arrive at staggered hours or take urgent calls. Manual queues fail to notify arriving patients, leaving waiting rooms clogged while doctors deal with emergencies.

Why Calendar Booking Systems (Practo / Google Calendar) Fail in Local Clinics

Common Examiner Question: "Why build a custom queue system instead of just using an appointment calendar like Practo or Google Calendar?"

The Technical Distinction: Appointment systems schedule patients into fixed time slots (e.g., 10:00 AM, 10:15 AM). However, healthcare outpatient consultations are inherently stochastic (variable duration):

  • A routine follow-up consultation may take 3 minutes.
  • A complex diabetic emergency examination may take 32 minutes.
  • An emergency walk-in patient must be admitted immediately, completely throwing off all downstream calendar appointments.

When a doctor running on a calendar slot schedule gets delayed by 25 minutes, every single patient scheduled for the rest of the day arrives on time and gathers in the waiting room anyway. In contrast, a dynamic queue state machine tracks the real-time consultation state and continuously calculates rolling wait times based on actual doctor consultation pace.

Concurrency & Atomic Token Sequence Generation

Examiner Favorite Question: "What happens when 50 patients press 'Book Appointment' at the exact same millisecond? How do you prevent duplicate token numbers?"

Defense: In high-concurrency environments, a naive Token.countDocuments() + 1 creates race conditions where two threads read the same count and generate identical token numbers (e.g. two T-005 tokens).

Our system eliminates this race condition entirely using MongoDB's atomic findOneAndUpdate operator: 

const counterDoc = await Counter.findOneAndUpdate(
  { _id: `COUNTER_${clinicId}_${doctorId}_${todayDateString}` },
  { $inc: { seq: 1 } },
  { new: true, upsert: true }
);
const sequenceNumber = counterDoc.seq; // Guaranteed unique and monotonically increasing
const tokenNumber = `T-${String(sequenceNumber).padStart(3, '0')}`;

Because $inc executes atomically inside MongoDB's document-level lock engine, no two concurrent requests can ever receive the same integer sequence number.

The Active Booking Key Lock

To prevent malicious spam or duplicate bookings by the same patient for the same doctor on the same day, we create a composite locking key: 

token.activeBookingKey = `${doctorId}_${date}_${normalizedPhone}`;

A unique sparse index on { activeBookingKey: 1 } causes MongoDB to reject any secondary booking attempt with a duplicate key error (code 11000). When the patient's token is transitioned to a terminal state (COMPLETED or CANCELLED), the key is cleared, freeing the patient to re-book if medically required.

6.0 Dynamic Wait Time Prediction Mathematical Model

The Mathematical Formulation

Estimated wait time is not a static guess; it is computed on-demand each time a patient tracks their token or requests an SMS status update:

Core Mathematical Formula: $$\text{EstimatedWaitMinutes}(T) = \sum_{i=1}^{P_{\text{ahead}}} \text{PacingFactor}(D, t)$$ $$\text{Where } P_{\text{ahead}} = \text{Count of active tokens ahead of } T \text{ in priority sort order}$$

Doctor Consultation Pacing Factor Calculation

  1. Case A (Cold Start — Fewer than 3 consultations completed today): $$\text{AvgDuration} = D.\text{avgConsultMinutes} \quad (\text{Baseline profile, e.g. 10 or 12 mins})$$
  2. Case B (Active Operating Clinic — ≥ 3 consultations completed today): $$\text{AvgDuration} = \frac{1}{N} \sum_{k=1}^{N} \text{consultationDurationMinutes}_k \quad (\text{Last } N \le 20 \text{ visits today})$$
  3. Bounding & Clamping: To prevent runaway mathematical anomalies from outliers (e.g. a doctor forgetting to click 'Complete' for 2 hours), values are clamped: $$\text{AvgDuration} = \max(2, \min(60, \text{AvgDuration}))$$

Display Range & Clinical Disclaimers

Because medical consultations have natural variance, our API never exposes a misleading single point prediction like "exactly 14 minutes". Instead, it computes a statistical interval:

  • Calculated Wait: 15 minutes
  • Displayed Range: 11 - 19 mins ($\pm 25\%$ window)
  • Mandatory Clinical Disclaimer: "Estimated wait is dynamic based on consultation pace and is an estimate, not a guarantee."

7.0 Security, Privacy & Zero-PII Architecture

Zero-PII Public Token Tracking Model

Traditional queue systems often expose patient names on public TV displays or URL parameters like /track?name=John&phone=9876543210. This violates modern healthcare data privacy guidelines.

Our system enforces a Zero Personally Identifiable Information (Zero-PII) public tracking model:

Attribute Internal DB Model (Staff Protected) Public Tracking Endpoint (/track/:uuid)
Patient Name Stored (e.g. "Sunita Rao") STRIPPED (Never returned)
Phone Number Stored (e.g. "+91 99999 00002") STRIPPED (Never returned)
Clinical Notes / Symptoms Stored in consultation record STRIPPED (Never returned)
Queue Position Available Exposed (e.g. "1 patient ahead")
Token Display Code Available Exposed (e.g. "DOC-GEN-101-001")
Doctor & Room Info Available Exposed (Dr. Priya Sharma, Room 101)
Estimated Wait Computed Exposed (~10 mins, 7-13 mins range)

Insecure Direct Object Reference (IDOR) Defense

A major vulnerability in hospital web apps is when Doctor A modifies Doctor B's queue by tampering with the URL parameter (e.g. PATCH /api/v1/doctor/tokens/123/action).

Examiner Question: "How do you stop Doctor A from calling or skipping Doctor B's patients?"

Defense: In server/src/services/doctor.service.js, our service verifies that the authenticated user's doctorId matches the target token's assigned doctorId: 

if (staffUser.role === ROLES.DOCTOR) {
  if (String(staffUser.doctorId) !== String(token.doctorId)) {
    const error = new Error('Forbidden: You can only call or update patients assigned to your room');
    error.statusCode = 403;
    throw error;
  }
}

Immutable Audit Trails

All sensitive actions (calling a token, skipping a patient, manual override) append an entry to the audit_logs collection containing: action, actorId, actorRole, targetId, previousState, newState, ipAddress, and userAgent. No DELETE or PATCH routes exist for audit logs.

8.0 Telephony, DLT SMS & Fault Tolerance

Indian Telecom Regulatory Authority (TRAI) DLT Compliance

In India, commercial bulk SMS must comply with Distributed Ledger Technology (DLT) regulations under TRAI. Every SMS template must be pre-registered with an approved Template ID and Sender ID.

Template Identifier DLT Template Name Exact Registered Template Content
DLT-GLB-001-BOOK Booking Confirmation [{Clinic}] Token {Token} confirmed for Dr. {Doctor} ({Dept}). Est. wait: {Wait} mins. Track live: {URL}
DLT-GLB-002-NEARTURN Near-Turn Alert [{Clinic}] Queue Alert: Only {Ahead} patient(s) ahead of Token {Token}. Please proceed towards consultation room for Doctor.
DLT-GLB-003-CALLING Calling Patient [{Clinic}] Attention: Token {Token} is now CALLED. Please proceed to {Room} for Dr. {Doctor}.
DLT-GLB-005-STATUS On-Demand Status [{Clinic}] Token {Token}: Status is {Status} with {Ahead} patient(s) ahead. Est. wait: {Wait} mins. Track: {URL}

Automatic Near-Turn Trigger Engine

When a doctor finishes with a patient and calls the next token, the server automatically queries all downstream waiting tokens for that doctor. Any patient whose queue position has dropped to ≤ 3 patients ahead receives an automated near-turn SMS alert.

A boolean flag nearTurnAlertSent: true on the token prevents duplicate alert spam if queue positions fluctuate due to cancellations.

SMS Failure Decoupling & Simulation Mode

A critical design requirement: A failure in the external telecom carrier must NEVER block a clinic from operating.

  • All Twilio calls are wrapped in safe try/catch blocks in sms.service.js.
  • If Twilio returns HTTP 400 (unverified test number) or HTTP 429 (rate exceeded), the error is logged to notifications as FAILED, but the database token creation returns HTTP 201 Success to the patient.
  • When SMS_ENABLED=false (default during academic testing), all SMS notifications are intercepted and simulated in terminal logs with zero carrier costs.

9.0 Front-End Engineering & Performance

Three.js Route-Level Code Splitting & Isolation

Examiner Question: "You used Three.js for 3D visuals. Doesn't that make the app heavy and slow on low-end patient phones?"

Defense: Three.js is strictly isolated to the public landing page (HomePage.jsx). It is completely excluded from clinical tracking and staff workflows using Vite's manualChunks configuration:

  • Landing Page Chunk: Downloads three-bundle.js (~794 kB) to render the 5-station clinic journey on high-end desktop browsers.
  • Live Tracker (/track/:uuid): Only downloads 11.8 kB of JavaScript. Low-end patient phones never load WebGL.
  • Zero-CPU Rendering Hook: The custom useCanvasVisibility hook monitors canvas visibility using the browser's IntersectionObserver and Page Visibility API, freezing the WebGL render loop whenever the canvas scrolls off-screen or the tab is minimized.

HTTP Polling vs. WebSockets Justification

Criterion WebSockets HTTP Short Polling (Implemented)
Mobile 3G/4G Stability Frequent disconnects; high socket renegotiation failure. Stateless; auto-retries seamlessly on mobile packet drops.
Server RAM per 10k Users High (10,000 persistent open TCP socket buffers). Zero persistent connection state in Node.js RAM.
Battery Drain Persistent socket keeps mobile cellular radio active. Radio sleeps between 10-second poll cycles.
Tab Inactive Throttling Socket stays open unless manually paused. Throttles from 10s to 30s when tab is hidden.

12.0 Top 25 Viva Voce Questions & Model Defense Answers

Q1: What is the main objective of this project?
To eliminate physical waiting room congestion in outpatient clinics by implementing a deterministic queue state machine with atomic token generation, dynamic rolling wait estimation, and zero-PII live mobile tracking.
Q2: Why did you choose React over traditional server-rendered templates (like EJS or Pug)?
React provides a dynamic single-page interface where queue metrics, doctor call notifications, and wait times update smoothly without full page reloads. Vite allows sub-second hot reloading and route-level code splitting so heavy libraries are never loaded on patient mobile devices.
Q3: How do you prevent race conditions when two patients book at the exact same millisecond?
We use MongoDB's atomic findOneAndUpdate with the $inc: { seq: 1 } operator on a daily counter document. MongoDB executes this operation atomically within its document-level write lock, guaranteeing strictly sequential integers (T-001, T-002) with zero duplicate numbers.
Q4: Why MongoDB instead of PostgreSQL or MySQL?
Clinical records naturally model as nested documents (operating schedules, consultation histories, and audit logs). MongoDB gives us atomic counter increments without multi-table row locking, schema agility for expanding doctor schedules, and seamless JSON alignment with our Express REST APIs.
Q5: What is the token priority ordering logic?
Walk-in patients are assigned deterministic priority ranks: Emergency (10), Differently-Abled (7), Elderly/Senior Citizen (5), and Standard (1). The queue engine executes .sort({ priorityRank: -1, bookedAt: 1 }), ensuring emergencies and elderly patients are scheduled ahead of general online bookings while preserving FIFO order within the same priority tier.
Q6: Can a standard patient starve if emergencies keep arriving?
In outpatient community clinics, emergencies average 1–2 per day. If a severe surge occurs, clinic emergency protocol redirects patients to a tertiary hospital ICU rather than an outpatient room. Standard patients never starve in normal clinical practice.
Q7: How does your dynamic wait time estimation algorithm work?
Wait time equals (Patients Ahead) multiplied by Doctor Pacing Factor. If the doctor has completed 3 or more visits today, the pacing factor is the rolling mean duration of completed visits; otherwise, it falls back to the doctor's baseline profile. Values are clamped between 2 and 60 minutes to prevent mathematical runaway.
Q8: Why did you choose HTTP polling over WebSockets for live tracking?
Local patients frequently move between unstable 3G/4G cellular networks where persistent TCP WebSockets drop and require complex stateful reconnection logic. Stateless HTTP polling with Cache-Control: no-store recovers instantly and leaves zero connection state in Node.js server RAM.
Q9: How do you prevent polling from overloading your server?
We utilize the Page Visibility API. While the tracker tab is visible, it polls every 10 seconds. When the user switches apps or locks their phone screen, polling automatically throttles to every 30 seconds, reducing server request volume by 66%.
Q10: What is Zero-PII tracking and why is it important?
Zero Personally Identifiable Information means the public tracking endpoint (/track/:uuid) strips patient names, phone numbers, and clinical notes. If a patient shares their tracking link or someone views their screen, no medical or personal data is compromised.
Q11: How do you prevent unauthorized token guessing?
Tracking URLs use UUIDv4 containing 122 bits of cryptographic entropy. With $5.3 \times 10^{36}$ possible combinations, brute-force guessing an active tracking UUID is mathematically impossible.
Q12: What prevents Doctor A from calling or skipping Doctor B's patients?
Service-level IDOR validation. In doctor.service.js, the API confirms that the authenticated staff user's doctorId from their signed JWT strictly matches the token's assigned doctorId. If they differ, the server returns HTTP 403 Forbidden.
Q13: How is staff authentication implemented?
Staff passwords are encrypted with Bcrypt using 10 salt rounds to defend against rainbow table attacks. Upon authentication, the server signs an HMAC-SHA256 JWT containing user ID, role, and doctor ID with an 8-hour expiration.
Q14: What happens if the Twilio SMS service goes down or runs out of credits?
The queue system never blocks or fails. All telephony operations are wrapped in non-blocking try/catch blocks. If Twilio fails, the token booking still completes successfully in the database, and the error is recorded in the notifications collection.
Q15: What is SMS simulation mode?
When SMS_ENABLED=false in .env, SMS messages are printed directly to the terminal stdout with full DLT headers and simulated delivery statuses, allowing zero-cost local testing and viva demonstration without spending telecom funds.
Q16: What is TRAI DLT compliance in SMS?
The Telecom Regulatory Authority of India requires commercial SMS templates to be registered on a blockchain Distributed Ledger Technology (DLT) platform with fixed headers and variable placeholders to prevent unsolicited spam.
Q17: When does the near-turn alert trigger?
Whenever a doctor calls or completes a token, the system evaluates all downstream waiting tokens. Any patient whose queue position reaches 3 or fewer patients ahead receives an automated near-turn SMS alert instructing them to head to the consultation room.
Q18: What is the purpose of the activeBookingKey?
It is a unique composite index key ${doctorId}_${date}_${phone}. It enforces that a single phone number cannot book multiple active tokens for the same doctor on the same day, preventing queue hoarding and denial-of-service spam.
Q19: How do you prevent NoSQL injection attacks?
We use custom sanitization middleware (sanitizeNoSql) that recursively strips keys starting with $ or containing . from req.body, req.query, and req.params, preventing operator injection such as {"$gt": ""}.
Q20: What security headers are configured in your application?
Helmet sets X-Content-Type-Options: nosniff, X-Frame-Options: SAMEORIGIN to prevent clickjacking, Strict-Transport-Security (HSTS) to enforce HTTPS, and Referrer-Policy: no-referrer.
Q21: Why is Three.js restricted to the landing page?
To maintain mobile performance and battery efficiency. Patients checking queue status need an ultra-fast, lightweight page. Isolating Three.js to the landing page ensures the tracking route bundle remains under 12 kB.
Q22: How do physical walk-in patients verify their token at the doctor's desk?
Reception prints or displays a high-contrast QR code encoding the tracking URL. The doctor or nurse scans it with the web camera scanner (/scanner), which instantly calls the verification API without manual typing.
Q23: How do you handle audit logging?
Every queue state change, manual receptionist override, and administrative update writes an immutable document to the audit_logs collection recording the actor, action, previous state, new state, IP address, and timestamp.
Q24: What are the primary limitations of the current implementation?
First, consultation duration estimation is reactive based on rolling averages rather than predictive of patient clinical complexity before examination. Second, rate limiting state resides in server RAM and would require Redis for a multi-instance cloud cluster.
Q25: What is the future scope for this project?
Integrating thermal receipt printers (ESC/POS) for physical ticket dispensing, automated multilingual voice announcements in waiting areas, and a federated multi-clinic network for district-wide patient referrals.
